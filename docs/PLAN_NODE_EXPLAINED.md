# شرح Node 3 (plan): الـ OOP والـ data structures من الصفر

الملف ده شرح جانبي لعبدالرحمن. مفيهوش كود بيتنفذ، ومفيش حاجة اتبنت لسه. هدفه تفهم ليه الشكل المعتمد كده، قبل ما نكتب سطر.

## 1. المشكلة اللي النود بتحلها

classify قال: الرسالة فيها جزء واحد، والـ intent بتاعه C1 (حالة الطلب)، والـ argument هو order_ref_1.

دلوقتي مين هيروح يجيب بيانات الطلب من الـ backend؟ مش الـ LLM. التصميم (D37) بيقول إن الكود هو اللي بينادي الـ tools، بخطة ثابتة لكل intent، ومفيش LLM بيقرر يستخدم tool إمتى.

النود دي هي اللي بتقول: الـ intent ده معناه ننادي الـ tools دي، بالترتيب ده، وبالـ arguments دي، ولو حصل كذا نعمل كذا.

## 2. تشبيه المطبخ

تخيل مطعم.

- الـ intent زي طلب الزبون على الورقة (الـ ticket).
- الـ PlanSpec زي كارت الوصفة: مكتوب فيه الخطوات والمكونات.
- الـ PlanExecutor زي الطباخ: بياخد الكارت وينفذه بالحرف.
- الـ Tools زي المخزن والتلاجة: الطباخ بيطلب منها ولا بيخترع.
- الـ OutcomeMapper زي مسؤول الجودة: لو المكون خلص أو فاسد، هو اللي يقرر نعمل بديل ولا نعتذر ولا نطلب مدير.

الفكرة: لو عندك 23 طبق، متكتبش طباخ ليه 23 `if`. اكتب كروت وصفات، وطباخ واحد عام يقرأ أي كارت.

## 3. إيه هو الـ PlanSpec بالظبط

هو صف في جدول. كل intent ليه صف واحد. الصف بيقول:

- الخطوات (steps) بالترتيب.
- كل خطوة بتنادي tool إيه، وكل argument ييجي منين.
- لو argument ناقص نعمل إيه (fallback أو سؤال توضيحي).
- لو الـ tool رجع status معين نعمل إيه، لو مختلف عن الافتراضي.

الصف نفسه بيانات، مش كود بيتنفذ. ده مهم لأن البيانات سهل تقراها وتراجعها وتختبرها، والـ intent الجديد بيبقى صف جديد مش `if` جديد جوه الكود. ده معنى مبدأ Open/Closed: مفتوح للإضافة، مقفول للتعديل.

## 4. الـ classes، واحد واحد

### PlanSpec
frozen dataclass. معنى frozen إنه ما ينفعش يتعدل بعد ما يتعمل. ليه؟ لأنه بيتشارك بين كل الـ requests، ولو حد عدّله في request هيبوّظ الباقي.

### ToolStep و FanOutStep
دول نوعين من الخطوات.

ToolStep بينادي tool واحد. مثال: order_details برقم الطلب.

FanOutStep بينادي نفس الـ tool على قايمة. مثال: C3 من غير رقم. العميل قال حالة المرتجع ومحدّدش أنهي طلب. المرتجعات جوه بيانات كل طلب (OrderView.returns)، وقايمة الطلبات الأخيرة (my_recent_orders) مفيهاش مرتجعات. يعني نجيب الطلبات الأخيرة، وبعدين ننادي order_details على كل واحد منهم (لحد 5) بالتوازي ونبص أنهي واحد فيه المرتجع. ده fan-out: خطوة واحدة بتتفرع على كذا نداء.

### ArgSource: مصدر الـ argument
كل argument له مصدر. أربع أنواع، وكل نوع class صغير بدالة واحدة اسمها resolve:

- FromArg: ياخد القيمة من Intent.arguments (اللي classify كتبها).
- FromRef: ياخد الرقم الحقيقي من ctx.order_refs. الـ LLM عمره ما شاف الرقم الحقيقي، شاف order_ref_1 بس. الكود هو اللي يحوّلها.
- FromResult: ياخد القيمة من نتيجة خطوة قبله، عن طريق selector (شرحه تحت).
- Const: قيمة ثابتة. مثال: W3 بيطلب fields ثابتة حسب نوع السؤال.

ليه 4 classes مش `if source == "arg"`؟ لأن كل نوع جديد بيبقى class جديد، من غير ما نلمس الكود الموجود. ده polymorphism: نفس الدالة resolve، وكل class بيتصرف بطريقته.

### الـ selectors
مثال: العميل قال "الساعة اللي طلبتها". classify طلّع item_clue = watch. الخطوة الأولى جابت قايمة الطلبات. دلوقتي مين الطلب اللي فيه watch؟ ده مطابقة في الكود على product_names.

الـ selector دالة بتاخد النتيجة السابقة وترجع القيمة. مسجلة بالاسم في dict. الجدول بيقول "استخدم match_item_clue" بالاسم بس، والدالة نفسها في الكود.

الثمن: الجدول مبقاش بيانات صرفة. هو بيانات زائد سجل دوال صغير. ده قرار واعي مننا، لأن المطابقة منطق مينفعش يتكتب كبيانات.

### Outcome و OutcomeMapper
كل نتيجة tool لازم تتحول لقرار. الـ tools بترجع واحدة من ستة statuses:

- ok: تمام.
- clarify: الرقم شكله غلط. ده مش denial، نسأل العميل.
- denied: مش موجود أو مش بتاعك. الـ tool نفسه سجّل الـ denial، فالـ plan مينفعش يسجله تاني.
- unavailable: الـ backend واقع أو الوقت خلص.
- data_issue: بيانات ناقصة أو متضاربة.
- not_implemented: الـ tool ده لمرحلة تانية (check_eligibility النهارده).

الـ Outcome قيمة من خمس: نكمل، أو template برقم، أو سؤال توضيحي، أو handoff بسبب وأولوية، أو رد محايد.

OutcomeMapper بياخد status وreason وبيرجع Outcome. فيه جدول افتراضي واحد لكل الـ intents، وكل intent يعدّل اللي يختلف بس. ده يمنع إن intent يتصرف مع denied بطريقة غير intent تاني.

حالتين خاصتين لازم تتعامل صح:

- worker: shipment_details ممكن يرجع ok مع reason اسمه access_window_closed وfields فاضية. ده مش نجاح عادي، ده معناه إن الشحنة خلص وقت الوصول لبياناتها.
- customer: order_details ممكن يرجع data_issue ومعاه بيانات. البيانات دي لا تُستخدم أبدًا، لأن فيها مشكلة.

### PlanExecutor
بياخد PlanSpec واحد لـ part واحد وينفذه خطوة خطوة: يحل الـ arguments، وينادي الـ tool عن طريق الـ Tools Protocol، وياخد النتيجة للـ mapper. لو الـ outcome مش "نكمل"، يقف.

### plan_node
رفيع. بيلف على الـ parts اللي ليها intent، وينفذ كل part بالتوازي (asyncio.gather)، وبيرجع dict بالتغييرات للـ state. مبيعدلش الـ state بإيده.

## 5. الـ data structures، ليه كل واحدة

- dict[intent_id, PlanSpec]: دور لكل دور. البحث بـ O(1)، يعني الوقت ثابت مهما زادت الـ intents.
- tuple للخطوات: الترتيب مهم، والـ tuple مينفعش يتعدل.
- dict[Status, Outcome]: جدول القرارات. الدمج: الافتراضي + تعديلات الـ intent، في سطر واحد.
- dict بالاسم للـ selectors: بحث سريع، وبيخلي الجدول يفضل بيانات.
- dict[(tool, argument), Task] لكل request: لو جزئين طلبوا نفس الـ tool بنفس الـ argument، ننفذ مرة واحدة ونشارك النتيجة. بيوفر مكالمات للـ backend.
- list[ToolRecord] في الـ state: list مش dict، علشان نداءين لنفس الـ tool بـ arguments مختلفة ميمسحوش بعض.

## 6. الأرقام والسرعة

الأرقام صغيرة ومحدودة بالتصميم: الـ parts لحد 3، الخطوات لحد 3، الـ fan-out لحد 5. يعني الـ CPU مش مشكلة أبدًا. الوقت بيروح في انتظار الـ backend (I/O).

علشان كده التوازي مهم: الوقت الكلي بيبقى أطول سلسلة، مش مجموع كل النداءات.

## 7. مثال كامل: C1 بدون رقم، بـ clue

العميل كتب: فين الساعة اللي طلبتها.

1. classify رجع: intent C1، item_clue = watch، من غير order_ref.
2. الـ executor يفتح صف C1.
3. الخطوة الأولى محتاجة order_ref وهو ناقص، فيستخدم الـ fallback: my_recent_orders.
4. ترجع قايمة الطلبات (ملخص: رقم، حالة، أسماء المنتجات).
5. selector اسمه match_item_clue بيدور على watch في الأسماء.
6. لو لقى طلب واحد: الخطوة التانية order_details بالرقم ده.
7. لو لقى أكتر من واحد أو ولا واحد: الـ outcome سؤال توضيحي.
8. ok من order_details يعني بيانات للـ template. باقي الـ statuses عن طريق الـ mapper.

## 8. إيه اللي مش بيتحل في الجدول

- لو الرسالة فيها جزئين ونتايجهم مختلفة (واحد ok وواحد denied) لسه معندناش AgentResult واحد يعبّر عن الاتنين.
- أرقام الـ templates لكل نتيجة (D68) لسه ما اتحددتش، فهتفضل stub لحد ما الـ 19 template تتبني.
- حقل الـ summary بتاع الـ handoff لسه مفيش قرار فيه.

## 9. التكلفة بصراحة

- فيه طبقات أكتر، فمحتاج تقرا الـ spec والـ executor مع بعض علشان تفهم intent واحد.
- الـ fan-out بتاع C3 ممكن يعمل لحد 5 نداءات للـ backend في request واحد.
- الـ selectors كود، مش بيانات.

مقابل ده: intent جديد يبقى صف جديد، ومعالجة الـ statuses في مكان واحد، وكل جزء ينفع يتختبر لوحده.
