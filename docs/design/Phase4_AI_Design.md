## Step 1 — Intents and division of work ✅

An intent is the user's purpose, not the words used. Fields (address, phone) are not intents. Answer sources: **Tool** (backend data via ④, D25), **Code** (⑤ calculations from structured values, D6/D13), **RAG** (ACTIVE policy text the caller may see, D7/D34), **Template** (⑪, fixed wording + structured values), **Handoff** (⑨, PRC-HOF-001 reason code + priority).

### Cross-cutting rules
- **Ambiguous order:** narrow by clues, show the user's own list, user picks, max 3 rounds (one round = one question + its answer), then handoff with clues; never pick randomly (POL-AGE-001 §4, System Analysis §2).
- **Unclassified intent:** after 2 attempts → handoff P4 (POL-AGE-001 §2); reason code = owner question. A classify failure (system error) and lost context are not attempts (D37, D65, N8 — an interpretation, design choice).
- **No ACTIVE document for an in-scope topic** → POL/P3 (POL-AIS-001 §3, POL-AGE-001 §2). Design choice (wider than the policy text): a document exists but the caller's role is not in its Audience → first try the D34 template path; if no template fact covers it → POL/P3; owner may later mark facts as customer-facing. D31 is only for topics outside scope.
- **Two ACTIVE documents give different rules (added, audit #3; revised N3):** POL-VER-001 §3 rule 3 first — the special-case document (POL-SPC-001) applies to the case it describes, which ⑤ does from structured values. For other linked rules, CODE compares the linked structured values (D47): equal → answer normally, no handoff; different → the Gateway must not choose: POL/P3 handoff, template 12 (POL-VER-001 §3 rule 4, POL-AGE-001 §2, POL-AIS-001 §3). Never decided by the LLM. How links are recorded and checked at upload → Phase 5 (upload safeguards). Until then, known gap: only linked rules are compared.
- **Safety first:** every part of a message is checked for SAFE/P1 before any backend call (CP-44); P1 overrides the whole reply. ⑪'s code P1 pattern check runs on every message in every mode, before and independent of classify (audit #1); it uses patterns for policy-defined P1 cases only, never single words (N1; Step 2, Step 5 D58).
- **Worker handoff wording:** tell the worker Dispatch or Customer Service has been notified and what to do meanwhile per the approved procedure only (PRC-HOF-001 §6); never promise a resolution or compensation (PRC-DIS-001 §4); timing follows Dispatch hours (POL-BUS-001 §5); non-P1 cases out of hours are queued (PRC-DIS-001 §5).
- **D30 multi-intent message:** answer all parts in one reply in written order; parts independent; each part identifies its own order; each 404 counts separately.
- **D31 no policy and no tool:** neutral reply, list what we can help with, offer a human only when helpful; never answer from the model's general knowledge.
- **D32 missing order:** clues against own recent list first (no denial); optional ask for the order number; typed number → backend, 404 counted as a denial (D4); fixed neutral not-found text; 3 rounds → INFO/P4; 3 denials → AUTH/P2; same turn → one AUTH/P2; order date before 2026-06-15 → handoff with migration note (POL-SPC-001 §8); worker missing shipment → always Dispatch, 404 still counted. **UNVERIFIED (audit #16):** designed without PRC-MIS-001 (missing-order procedure, which POL-RET-001 §7 points to); re-check when docs 04–10 are added.
- **D33 several handoffs from one message:** different reason codes → separate tickets; same code → one ticket; AUTH absorbs same-turn INFO from the same identification attempt; each ticket has only its own §3 fields, its own outbox row and Idempotency-Key; content-free sibling line; one reply names both cases with a channel-based reply time; D28 wins in Degraded mode. (D70's "highest severity wins" applies only within one case or part, audit #18.)
- **D34 use vs show:** the code may act on any ACTIVE document whose Audience includes "AI Gateway"; text shown or explained only from ACTIVE documents whose Audience includes the caller's role; Confidentiality is stored but does not gate; facts a policy orders us to tell are structured values tied to document version, told through templates; internal rules are never explained (design choice).
- **D35 worker denials (scope: delivery workers):** (1) shipment not his (backend 404) → counted (D15, POL-DWA-001 §3/§7); (2) always-forbidden data — email, payment except COD amount, other orders of the customer, customer history, internal notes (POL-DWA-001 §5 "No"; §6 "Denied" for email and all orders; GDL-DTS-001 §4) → counted. **Labelled (audit #13): this row is an INTERPRETATION, not policy-literal.** POL-AGE-001 §2 "3 or more denied requests" has no exception, but POL-DWA-001 §7 escalates "attempts to access non-assigned shipments" and §6 treats an email request as an ordinary denial with a permitted alternative. Counting field denials therefore **amends Phase 3 D15's closed denial list** (backend 404 on a specific record, worker assignment mismatch), recorded as such in the Phase 3 doc; (3) field closed by the access window on his own delivered shipment (POL-DWA-001 §4 delivered rows: ID and status only) → NOT counted (CP-47); (4) reassigned shipment → counted: POL-DWA-001 §4 says "Denied immediately" and the Gateway cannot tell it apart from "never his" (both are a backend 404, D4) — default taken on his behalf, policy-literal; an innocent worker reaches a human at P2 with no accusation. ~~At most ONE counted denial per user turn~~ → **amended by D41** (Step 2): resource denials count each; field/query denials about his own shipment count at most once per turn. Counting is done by CODE (the shared ④/⑤ library, on every path, N2) when a request asks for a forbidden field or query (Step 3: worker tools get an explicit requested-fields / query-type enum checked against a deny-list); the LLM only maps the user's words to that enum, like extracting an order ID, and a query denial needs another worker's id in the message as code evidence (audit #13, N10; see D41). The reply is neutral and names a permitted alternative only when the policy text gives one (POL-DWA-001 §6: phone; POL-AIS-001 §2.3). After the 3rd counted denial in a login session → P2; for non-assigned/reassigned shipments the worker is told the request is being reported to dispatch (POL-DWA-001 §7); for field denials the wording is "Dispatch or Customer Service has been notified" (PRC-HOF-001 §6). CP-68's "allowlist miss is not a denial" refers to the customer's ③ order list (D5). P2 routing per POL-ESC-001 = UNVERIFIED. Customer-side equivalent (customer asking for worker or internal data, POL-PRV-001 §2) → decided in Step 3 (D45: not counted).
