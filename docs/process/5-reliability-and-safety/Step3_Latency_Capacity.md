# Phase 5 — Step 3: Latency & Capacity budget

Adaptive AI Gateway · NovaCart · القرارات المقترحة D91–D98

## الفكرة في سطرين
الـ Step 2 قررت **إزاي** الـ Gateway يتصرف لما حاجة تبوظ. الـ Step 3 بتحط **الأرقام**: كل خطوة تاخد قد إيه من الوقت، وكل حاجة حدودها قد إيه، ونختبر ده إزاي.

التشبيه: ميزانية بيت. عندك 8 ثواني "فلوس" لكل طلب، والهدف إن 95% من الطلبات تخلص في 5 ثواني. لازم تقسم الميزانية على البنود، وتعرف لو الفلوس قربت تخلص هتلغي أنهي بند الأول.

## اللي جاي من السياسات والقرارات اللي فاتت (ثابت)
- 8 ثواني للطلب كله، وretry مرتين (1 ث ثم 2 ث) للـ backend (POL-BDR-001).
- 5 ثواني لـ 95% من الطلبات مع 20–50 مستخدم، وDegraded mode مع 1,000–2,000 مستخدم (Phase 3).
- طابور 3 دقايق في Degraded mode، وبعدها handoff (Phase 3).
- 3 جولات توضيح بالكتير (POL-AGE-001).
- بيانات الحالة أقدم من 5 دقايق بتتعمل refresh مرة واحدة (POL-BDR-001).

## تنبيه مهم عن الأرقام
كل رقم مكتوب جنبه **(قيمة مبدئية)** هو design choice وASSUMPTION. مش من السياسة، وهيتقاس ويتظبط في الـ load test (Phase 6) والـ evals (Phase 8). الهدف إن يبقى عندنا نقطة بداية مكتوبة، مش إننا ندّعي إنها صح.

## D91 — ميزانية الوقت لكل خطوة، وترتيب القطع

### الخيارات
| الخيار | المميزات | العيوب |
|---|---|---|
| أ) من غير ميزانية؛ كل خطوة تاخد اللي هي عايزاه لحد الـ 8 ث | بسيط | الـ p95 هيعدّي 5 ث؛ خطوة بطيئة تاكل وقت الباقي |
| **ب) ميزانية لكل خطوة + ترتيب قطع ثابت (المقترح)** | الـ 5 ث بتبقى هدف قابل للقياس؛ عارفين نقطع إيه الأول | أرقام كتير نقيسها ونظبطها |
| ج) نقطع الـ LLM كله لو الطلب اتأخر | سريع جداً | الإجابات اللي محتاجة شرح تتحول handoff كتير |

### المقترح (قيم مبدئية)
| الخطوة | الميزانية |
|---|---|
| فحص P1 + safety gate + plan (كود) | ~0.1 ث |
| classify (موديل صغير) | ≤ 1.0 ث |
| backend + RAG بالتوازي | ≤ 1.5 ث في الحالة العادية |
| جولات الـ agentic RAG الزيادة | بس لو الوقت المتبقي يسمح |
| reply (موديل كبير) | ≤ 2.0 ث |
| validate + render | ≤ 0.2 ث |
| **المجموع العادي** | **~4.8 ث**، والباقي لحد 8 ث هامش للـ retries |

### ترتيب القطع لو الوقت قرّب يخلص
1. نلغي جولات الـ agentic RAG الزيادة (K → 0).
2. نلغي نداء الـ judge+rewrite.
3. الجزء اللي محتاج شرح ياخد template لو موجود، وإلا template 18 ("ماقدرتش أكمل الجزء ده دلوقتي" + عرض human).
4. الـ retries بتقف لما الوقت المتبقي ما يكفّيش محاولة كاملة (D83).

**عمرنا ما بنقطع:** فحص P1، والـ safety gate، والـ validate. دي أمان، والأمان رقم 1.

## D92 — الـ LLM timeout والحد الأدنى للوقت
| الخيار | المميزات | العيوب |
|---|---|---|
| أ) timeout ثابت (مثلاً 3 ث) | بسيط | لو الـ backend كان بطيء، الطلب يعدّي الـ 8 ث |
| **ب) timeout = الوقت المتبقي − هامش، وما نناديش الـ LLM لو الوقت أقل من حد أدنى (المقترح)** | متسق مع D27 وD75؛ ما بنبدأش نداء هيتقطع | محتاجين نقيس الهامش |

**قيم مبدئية:** الهامش = 0.5 ث (للـ validate والـ render والإرسال). الحد الأدنى لنداء الـ reply = 1.5 ث، ولنداء الـ classify = 0.8 ث. لو الوقت أقل من كده، نروح لـ template أو handoff على طول.

## D93 — حدود الرسالة والطلبات
| الحد | القيمة المبدئية | ليه |
|---|---|---|
| N = عدد الأجزاء اللي بنجاوبها من رسالة واحدة (D40) | 3 | رسالة فيها 3 أسئلة بتخلص في الميزانية؛ الباقي بنقوله للعميل |
| أقصى طول للرسالة | 1,000 حرف | بيحمي الـ tokens والوقت، وبيصعّب الـ injection الطويل |
| عدد نداءات الـ backend في الدور الواحد | = N (3) | جزء واحد = lookup واحد |
| جولات التوضيح | 3 (من السياسة) | POL-AGE-001 |
| Rate limit لكل login session | 20 رسالة/دقيقة | إنسان عادي مش هيكتب أسرع من كده |
| Rate limit قبل الـ token check (لكل IP) | 60 طلب/دقيقة | بيوقف الـ tokens المزيفة (T5b) من غير ما يأذي شبكة عليها كذا مستخدم |
| رسايل مستنية في الطابور لكل chat | 3 | بيحمي الطابور من chat واحد |

البديل اللي رفضناه: من غير حدود. ده بيخلي رسالة واحدة طويلة تاكل ميزانية 10 مستخدمين.

## D94 — أرقام الـ RAG
| الرقم | القيمة المبدئية | ليه |
|---|---|---|
| top-k (عدد الأجزاء المسترجعة) | 5 | كفاية للسياسات المرتبطة ببعض، ومش بيطوّل الـ prompt |
| K = أقصى جولات agentic زيادة | 1 | جولة واحدة بتصلّح أغلب الأسئلة الصعبة، والتانية نادراً بتفرق وبتاكل وقت |
| حد الـ score gate | يتحدد من الـ eval set (Phase 8) | رقم بالتخمين هنا مالوش لازمة |
| أقصى أجزاء في الطلب كله (D59) | 8 | حد إجمالي لكل الجولات |

البديل المرفوض: K = 2 أو أكتر. بيكسر الميزانية، وتجربة D78 هي اللي هتقرر لو الـ agentic نفسه يستاهل.

## D97 — سعة الـ DB والـ Ticketing
- **DB connection pools:** pool لكل instance، وpool منفصل للـ retrieval (D48)، وpool للـ Worker. والمجموع لازم يبقى أقل من حد الـ PostgreSQL بهامش. لو الـ pool مليان، الطلب بيستنى وقت قصير (قيمة مبدئية 0.5 ث) وبعدين fallback. ما بنفتحش connections لا نهائية.
- **ACTIVE policy ids:** بنقراها مع كل طلب من غير cache (Phase 3). ده تمن معروف، والـ load test هيقول لو محتاج cache قصير جداً. مش هنغيّره دلوقتي.
- **Ticketing burst (blocker 5):** نحسب أقصى معدل handoffs وقت الذروة (رسايل الطابور اللي خلص وقتها + BKD + الـ P1)، ونتفق مع صاحب الـ Ticketing على السعة. لو مش قادر، الـ outbox بيصفّ التذاكر (مفيش حاجة بتضيع)، بس العميل يتقاله "هيرد عليك CS" من غير وقت محدد.

## D98 — خطة الـ load test (التصميم هنا، والتشغيل في Phase 6)
| السيناريو | اللي بنقيسه | معيار النجاح |
|---|---|---|
| عادي: 20–50 مستخدم | p95 | ≤ 5 ث، ومفيش طلب يعدّي 8 ث |
| ذروة: 1,000–2,000 مستخدم + 429 من الـ LLM | Degraded يشتغل، سرعة تفريغ الطابور، الـ handoffs | الـ templates فورية، ومفيش رسالة تضيع |
| السلسلة R4: backend بطيء + 429 + Ticketing بطيء | عمر أقدم تذكرة، والـ P1 lane | P1 بيطلع الأول دايماً |
| هجوم tokens مزيفة | الـ rate limit قبل الـ token، والـ JWKS refresh | الـ backend ما يتضغطش، والـ Degraded ما يشتغلش بالعافية |
| Redis وقع | Degraded + limits محلية | مفيش fail open |
| الـ Worker وقع | الـ alert من برّه | الـ alert يطلع قبل ما الـ P1 يتأخر |

**سؤال الـ availability (99%):** هل وقت الـ Degraded mode بيتحسب "شغال"؟ ده سؤال للـ owner (Business/Operations). المؤقت المقترح: بيتحسب شغال طالما الـ templates والـ handoffs شغالين، وبنسجّل وقت الـ Degraded لوحده عشان الـ owner يشوفه.
